# KD Designer - project guide for Claude

Show controller on an **Arduino Portenta H7** (M7 core, Mbed OS Arduino core), inspired by
Pharos Designer 2: DMX / Art-Net / sACN output, timelines with tracks and effects, triggers,
projectors (PJLink), PCs, UDP/OSC/TCP/HTTP/Modbus, a web UI for programming and a touch panel.
Everything (web UI, project, logs, images) lives on a USB stick. The user (Jaromir) is a show/AV
technician; explain in plain words, he reads the README rather than the code.

`README.md` is the user manual and feature list - read it first for what exists. `NEXT-STEPS.md`
lists known loose ends and the planned tidy-up.

## Layout

## Rules that are not obvious from the code

- **Things that exist in several places must change together:**
  - **Commands**: firmware `src/Cmd.cpp` (+ `Triggers.cpp` for conditions; device-driver commands in `Drivers.cpp` `*Cmd()`), mock `tools/mock-server.js` (`exec`, `checkCondition`, `drvCommand`), and the UI grammar `GRAMMAR` / `COND_GRAMMAR` in `app-grammar.js` (autocomplete, validation, highlighting, builder, hover help: `matchPart`, `completeBase`, tips, `builderField`).
  - **Effect language**: `data/www/fx.js` and `src/Fx.cpp` - same syntax, opcodes, function numbering, outputs and the integer `rand` hash. `toFixture()` in fx.js = `runEffect()` in Show.cpp = `effectFrame()` in the mock. Firmware only: `prepare()` in Fx.cpp splits the bytecode into a per-frame part (statements and pieces that don't depend on i/u/x/y) and a per-fixture part, and folds operands into instructions; `runEffect` resets only the outputs and inputs per fixture. Run `node tools/fxtest/test.js` after any change to either file.
  - **Project parsing**: `Show::parse` (ShowParse.cpp) / `State::load` / other `load()`s in the firmware (a new module's `load()` goes in `Project::loadModules`), `normalize()` in app-core.js, and the mock.
  - **Machine Control I/O** (`machineControl` in project.json, points `in0-7 out0-7 io0-11 ai0-2 ao0-3`): firmware `src/Board.cpp` (only built with `-DKD_BOARD_PMC`, env `machine_control`; the default env has no I/O), mock `board*` functions, UI `PMC_*`/`pmc*` in app-core.js, the Machine Control tab in app-drivers.js, the `io` command/condition in the grammar, and the `input` trigger's `io`/`level`.
  - **Project rules** in `model.js` (UI + mock) mirror `ShowParse.cpp`: channel names `dim/intensity/i/master`, `r/red`, `g/green`, `b/blue`, `w/white` (`channelRoles` / `colorSlots`), track fixture order, first-map position, fade paths (`EASE` / `ease()` in Show.cpp).
  - **Device history** (Monitoring device view): `Monitor::record` / `flushHistory` / `historyJson` + `Log::search` in the firmware (`/api/history`, `/api/devlog`), `histRecord` / `flushHistory` / `historyLines` / `logSearch` in the mock, `histSegments` / `histGraph` in app-system.js (day-file line format `epoch state kind name`, state `online|offline`, `on|off` projector power, `p:<key>=1|0` show-device reading; `boot`/`alive`, the 600 s alive / 900 s gap rule). Every place that changes a device's online state (or projector power) calls `record`, including the first check; readings are recorded in `setPoint` (Drivers.cpp) / `drvSet` (mock), and which ones count as on/off is `onOff()` = `drvOnOff()`. Log lines match the name/IP as a whole word (`hasWord`).
  - **Touch-panel control state** (`panel <name> text|color|flash|value|enable|disable|reset`, `label`, values sent with `/api/panel?…&value=&vars=name=v;name=v`): `State::setControl` + `statusJson` "labels" and `Web.cpp` `/api/panel` in the firmware, `ctl()` / `/api/panel` in the mock, `panelCtlState` / `panelUpdate` in panel-ui.js. Variable links (`var`, `links.r/g/b/h/s/v/x/y`, `rgbScale`) are worked out by the panel only (`panelLinkValues` out, `panelLinkedValue` back). Panel triggers get `{value}` (and `{r} {g} {b}` for `#rrggbb`, `{x} {y}` for `x,y`) in `Triggers::panelEvent` and the mock.
  - **Device groups** (`deviceGroups`, `kind` = pc | projector | tcp | a show-device type; none = network): `State::groupMembers` / `forMembers` used by `pc`, `projector`, `send tcp` in Cmd.cpp and `Drivers::command`; mock `kindGroup` / `forMembers`; UI `groupsSection` (app-system.js) and `kindGroups` / `findKindGroup` in app-grammar.js. A real device name wins over a group of the same name.
  - **Show files** (`.kdshow` = `{ kdshow: 1, exported, project, media: { name: base64 } }`, media = map backgrounds): `exportShow` / `openShow` in app-system.js and `readKdshow` / `ctlKdshow` / `import` in tools/launcher.js. The launcher finds controllers by the ArtPollReply short name "KD Designer" (`sendPollReply` in Net.cpp) and reads `/api/status` `version`/`project`/`update.target`.
  - **Mode groups** (`modes`: `startup`, `var`, `stateInfo` per state with `enter`/`leave`/`color`/`icon`; trigger `onlyIn`): `State.cpp` (power-up state, `previous`, `since`, history `mode:<group>` / `m:<state>`), `Triggers::changeMode` (leave, enter, mode triggers, variable) with the enter/leave actions as hidden Manual triggers from id 20001, `onVariable` (variable -> mode), the `onlyIn` check in `runTrigger`; the mock's `changeMode` / `modeLoad` / `stepState` / `trigById`; the Modes page and `modeProblems` in app-system.js, `onlyInField` in app-triggers.js, the panel header in panel.html.
  - **Clock maths**: `src/Clock.cpp` (days, summer time, sunrise/sunset, calendar periods) = `days` / `inPeriod` / `sunUtc` in `model.js` (used by `Sched` in app-system.js and `SchedM` in the mock).
- **Timeline clip length** (`len`/`out` on a cue): the firmware turns it into a release cue (`pushCue` in ShowParse.cpp, `release`/`from` in `Cue`) and fades the track's opacity (`TrackFade.op`, `endRelease` in Show.cpp); the mock mirrors it (`timelineEvents`, `endRelease`). No `len` = hold until the next cue (old projects). The editor is in app-show.js (`tlGridHtml`, `resolveOverlaps`, `splitAtCursor`).
- **Trigger runs**: `sleep`, `wait until` and `repeat <n> times every` schedule the rest of a trigger's actions (`Scheduled` in Triggers.cpp with `kind`; `line >= 0` = part of a run, which is what "while running" and the UI's ⏳ look at). The same in the mock (`runActions`, the 50 ms scheduler) and the UI grammar (`splitHead` / `validateHead` in app-grammar.js: the condition or command after the head uses its own grammar). Cooldown, while-running, hold/double, sequences and the fire history (`remember`, `/api/trighistory`) are mirrored in the mock's `runTrigger`.
- **DMX input** (`dmx_in` triggers): the receive thread (`NetRx`, handlers `artIn` / `sacnIn` in Net.cpp, under `inLock`) keeps up to `KD_MAX_DMX_IN` received universes that `Triggers::load` asks for (`Net::setDmxInputs`); triggers read a copy (`dmxInFrames` / `dmxInCopy`). ArtPoll is answered from `Net::poll` (main loop, `pollAsked`). The sACN socket joins one multicast group (reopened with `NetRx::unwatch`/`watch` around it). The mock has no network input: `dmxin <artnet|sacn> <universe> <channels> <value>` in its console.
- **Triggers are renumbered in list order** (`renumberTriggers`); separators get ids 10001+. References by number in actions, timeline trigger cues and sequence `steps` are rewritten on renumber; by name on rename (`renameTriggerRefs`). Name references are preferred.
- **Fixture types are UI-only.** A fixture in project.json stays `channels: [...]`; `type` ("Maker / Model"), `mode` and `icon` only drive the UI, and `p.fixtureTypes` (array of type texts) holds the project's own types. Library channel names (`oflName` in fixture-lib.js) must start with a prefix in `isExemptChannel` (ShowParse.cpp) unless they are intensity/colour - keep both lists in step.
- **The firmware drops UI-only data after loading** to save RAM: trigger `notes`, fixture `type`/`mode`/`icon`, `fixtureTypes`, `triggerColorNames` (colour-tab names), `maps` (positions are copied for effects first) and `effects` (compiled). `/api/project` GET still serves the full file from the stick.
- **Map images**: uploaded at once to `show/media/`, but a replaced/removed image is only deleted after the next successful save (`S.mediaTrash`).
- **Threads**: anything touching the engine holds `g_engine` (rtos::Mutex). Events (timeline end, trigger cues, device state, variables) are queued and handled in the main loop. `netrx` and lwIP's `lwip_tcpip` (raised in `NetRx::begin`) run AboveNormal, above the main loop. Sockets the receive thread reads are opened/closed only between `NetRx::unwatch` and `watch`, and sent on with `sendTo` (not `beginPacket`/`endPacket`: those switch the socket to blocking). A `reload` from a trigger's actions waits for the run to end (`Cmd::reloadDue` in the main loop): it replaces the trigger table that run reads.
- **Memory budget**: RAM ~27 %, flash ~79 % (Machine Control build ~28 % / ~86 %: full newlib since 9 Nov 2026 costs ~35 KB), with `KD_MAX_UNIVERSES` 8 (~20 KB RAM per universe). Three places:
  - **Heap** (~375 KB, internal RAM): ~196 KB used with an empty show (thread stacks, network, USB), ~100 KB free with the feature demo. Every connection, String and small JSON lives here; blocks up to 256 bytes come from a 48 KB pool inside it (`HeapPool.h`; its free bytes are added to the free-heap figure). The trigger table is not here (SDRAM).
  - **D2 SRAM** (`src/D2Ram.*`, 256 KB at 0x30000000): playback buffers `pbs` (~140 KB, `D2Ram::array`) and the log ring (~68 KB, `D2Ram::keep`: not cleared on reset, so the log, the start reason and the breadcrumbs `Log::crumb` survive a watchdog/crash restart).
  - **SDRAM** (8 MB, `src/BigRam.*`): the project text and JSON (`JsonDocument(BigRam::json())`), the engine tables (`BigRam::Vec<T>`: fixtures, scenes, timelines, cues, effects), the trigger table (its action lines point into the project JSON), the receive queue (`NetRx`), and big replies (`BigRam::Text` for status/log). **Never hand SDRAM memory to the network or other DMA**: data sent straight from SDRAM arrived garbled; `writeAll` in Web.cpp copies it to internal RAM first. Thread stacks stay in internal RAM for that reason.
- **Arduino core fixes** (found on the first hardware run, 6 Nov 2026): `tools/core/variants/PORTENTA_H7_M7` is the core's variant with a `libmbed.a` rebuilt for 32 lwIP sockets (Arduino's has 4; `board_build.variants_dir`; rebuild in WSL per `tools/core/README.md`; `lwip.mem-size` can't grow, it has a fixed 16 KB slot). `lib/SocketWrapper` is Arduino's with the `readSocket` busy-loop fixed, a non-blocking `write()` and a time limit on `connect()` (see `lib/README.md`). Threads that mostly wait on the network run at `osPriorityNormal` (BelowNormal starved them for tens of seconds behind the main loop); `board` stays BelowNormal; `dmx` is AboveNormal (it sleeps while the UART TX interrupt sends the slots, starts a frame on `Dmx::commit()` after each engine tick so every engine frame goes out once, and makes the break as a 0x00 byte at a low baud rate: Mbed's `serial_break_set` break is only ~44 µs; every baud switch first waits for the UART's TC flag, `waitIdle`, or the fixture drops the frames). `-DWIFI_UDP_BUFFER_SIZE=1024` because Arduino's UDP class cuts packets at 508 bytes. Mbed's STM32 Ethernet driver ignores multicast joins (MAC filter drops them): `macAcceptGroup` in Net.cpp opens the hash bin. `Ethernet.linkStatus()` means "has an address", not "cable in": the cable is read from the PHY (`readPhy`, on Mbed's shared event queue like the driver's own PHY poll). Our `variant.cpp` calls a weak `kdBeforeBootloader()` on the 1200-baud upload touch. A PlatformIO update of `framework-arduino-mbed` means redoing these.
- **Show-device readings** ("points") have keys per type (`1.3` Kiss-Box slot.channel, `1/2/3` KNX, `out1`/`in1` NETIO, `tl1`/`sc1`/`grp1` Pharos, `scene`/`master` DiGidot, `msg` BrightSign; with the kdlink plugin also `z1` (zone state), `z1.file`, `var.<name>`, `gpio0-7`, `serial`, plus `states` (test buttons) and `activity` (last 30 lines) in the status). The BrightSign plugin `data/www/brightsign/kdlink.brs` (BrightScript, runs in the presentation) talks tab-separated `kd …` UDP in and one JSON object per packet out: keep it in step with `pluginSend`/`pluginPacket` in Drivers.cpp and `bsPlugin`/`bsReport` in the mock; `vars` (and KNX address `var`) link them to variables, in Drivers.cpp, the mock (`drvLinks`) and app-drivers.js. Kiss-Box `names`/`commands` are UI-only and dropped by the firmware. Per playback per universe there are several 512-byte arrays (`KD_MAX_PLAYBACKS` 8, `KD_MAX_UNIVERSES` 4, `KD_MAX_TRACKS` 16) - check the build's RAM line after engine changes.
- **UI performance with big rigs** (~600 fixtures, 4 full universes): `fixture(id)` and `findType(key)` use indexes - use them in loops, don't `.find` on `P().fixtures`. Never emit a `<select>` of all fixtures per row (the Scenes table did: 36 MB of HTML); build heavy parts only when shown. Maps with > 40 fixtures are `.dense` (no icons, glow or transitions). Test with a generated big project on a copy.
- **UI size = CSS `zoom` on `<html>`** (`applyUi` in app-core.js, Settings > Display; theme = `data-theme` with colour tokens in style.css - use the tokens, no hard-coded chrome colours). `clientX` / `getBoundingClientRect()` are screen pixels: divide by `uiZoom()` before writing them into `style.left`/widths (ratios are fine; `offsetWidth`/`clientWidth` are already CSS pixels). Use `var(--vh)` / `var(--main-h)` instead of `vh`, and `.narrow` instead of a width `@media` query.
- **Speed traps found by the stress test (9 Nov 2026, `tools/stress/`, results in README "Capacity (measured)")**, don't undo:
  - `platformio.ini` `build_unflags = -mfloat-abi=soft --specs=nano.specs`: PlatformIO's builder forced software floating point and newlib-nano. Check `.f64` instructions in a disassembly if maths gets slow again.
  - **Data cache**: Mbed's H7 Ethernet driver switches it off at start; `cacheOn()` in Net.cpp switches it on again (write-through `FORCEWT`, MPU region 4 = Ethernet `Rx_Buff` uncached, rechecked every second in `maintain`). SDRAM is write-back cached (`BigRam.cpp`, MPU region 5). So **nothing may hand cached memory to DMA**: network sends from SDRAM go through `writeAll`'s bounce buffer, big stick reads/writes through 512-byte buffers (`Storage.cpp`). The USB stick, DMX UART, QSPI and Machine Control I/O are CPU-driven.
  - **Heap**: `src/Heap.cpp` replaces Mbed's malloc wrappers (needs the weakened symbols in `libmbed.a`, see `tools/core/README.md`) and serves small blocks from `HeapPool.h` (malloc+free 0.43 µs instead of 2.8: newlib's lock is an RTOS mutex). The pool must stay a zero-initialised global without a constructor (malloc runs before global constructors). Still keep allocations out of per-packet / per-fixture / per-frame paths. `String::equalsIgnoreCase("literal")` and `substring()` allocate: compare with `strcasecmp` / `strncmp` in place. Don't make newlib's heap lock a critical section (tried: the board hung at boot, no USB; recovery = bootloader + dfu-util, see HARDWARE-TEST-PLAN).
  - Engine tables keep no Arduino Strings per fixture (`Slot::name` points into the project JSON), and project loading looks fixtures up by id index (`fixIdx` in ShowParse.cpp), never by searching the list.
  - The stick's log is written by its own thread (`Log::startWriter`, BelowNormal); UDP/OSC trigger messages get `KD_UDP_BUDGET_US` per main-loop round, bursts (`repeat <n> times` without every) `KD_BURST_BUDGET_US`. Hundreds of log lines a second still slowed everything (stick writes): at most `KD_TRIGGER_LOG_PER_S` "fired" lines per trigger per second.
  - The firmware is built with `-Os`: hot functions are `KD_FAST` (`optimize("O2")`, Show.cpp / Fx.cpp) and their helpers `KD_HOT` / `always_inline` (`testBit`, `roundInt` = lroundf as one VCVTA instruction): with `-Os` even `testBit` was a function call per channel. GCC won't inline across different optimize attributes, so a helper used by a `KD_FAST` function needs one of the two. Not file-wide: that cost ~25 KB flash.
  - `LOGD`/`LOGI`… check the level before evaluating their arguments (`KD_LOG` in Log.h). `Cmd::tokenize` makes one String per word (`+=` per character re-allocated each time). `Vars::set` reserves 8 (a growing `std::vector<String…>` copies every String: Arduino's move isn't noexcept).
  - `/api/status` `stats.tickParts` (µs per frame: fx, fade, mix, out), `trigUs`, `busyUs`, `udpDropped`: look there first when something gets slow.
  - The PC stress tool must pace evenly (`pace` in stress.js): Windows timers made bursts of ~50 packets, and the Ethernet chip holds ~7 back-to-back packets.
- Keep C++14 (no `if` with initializers, no structured bindings); `bit` is an Arduino macro (use `testBit`); chrono literals need `using namespace std::chrono_literals`.

## Build and test

- Firmware: `python -m platformio run` (PlatformIO is installed as a Python module; libraries come from the PIO registry). First run on real hardware: 6 Nov 2026, a Portenta Machine Control (`-e machine_control`) on COM3, IP by DHCP (172.16.1.171 on the office network); results and what is still untested in `HARDWARE-TEST-PLAN.md`. When the board is plugged in: upload with `-t upload --upload-port COM3`; the serial log replays the recent lines when a monitor connects; `/api/status`, `/api/log`, `/api/cmd` and `PUT /api/update` work over the network. Test with a test project (not the user's show: its triggers talk to real devices), Art-Net unicast to the PC.
- Git: the user commits in Sourcetree. `git` is not on the PATH; use
  `& "$env:LOCALAPPDATA\Atlassian\SourceTree\git_local\bin\git.exe"` to look at status/diffs, and
  leave committing to the user unless asked.
- No native C++ compiler on Windows, but WSL (Ubuntu-22.04) has g++: `node tools/fxtest/test.js` (effects) and `tools/heaptest` (allocator). Keep `Fx.cpp`'s language a line-by-line mirror of fx.js.
- UI: start the preview **"mock"** (`node tools/mock-server.js 8080`), then check the feature in the browser pane with real clicks/keys where possible and look at `__errs`/console errors. `node --check data/www/app-*.js` (one file at a time) catches syntax errors (template literals break easily). The browser pane often clicks in the wrong place by coordinates: click by `ref` from `find`/`read_page`.
- **The user often has the mock open in his own browser and saves real work into `data/show/project.json`.** Don't save test edits over it: reload without saving (`S.dirty = false; location.reload()`), or test on a copy (copy `tools/` + `data/` to the scratchpad and run the copy on another port). Saving reloads the project, which fires the Startup trigger (which starts "Inloop" after 5 s and releases group A timelines) - wait for that when testing playback.
- Keep the README up to date with every user-visible change.

## Style

- Comments explain *why*; match the surrounding density. UI text and README in plain English, short.
- Vanilla JS: `$`/`$$` helpers, `render()` rebuilds the current view from `views[S.view]()` and runs `views[S.view].after()`; data binding through `data-p="path"` (+ `data-t` type, `data-r` re-render on change); state in `S`; project via `P()`; `markDirty()` after edits.
- Page keyboard shortcuts go in `views.<page>.keys = (e) => …` (one global handler calls it when not typing; Ctrl+S is global). Animations/polls use `pageAnimation(name, frame)` / `pagePoll(name, fn, ms)` so `render()` stops them. Links to another item use `data-goto-trigger|timeline|effect="<id>"` (handled globally, no per-page wiring).
- The UI files share one global scope: code that runs at load time may only use what earlier files define; everything else is called later and can live in any file.
